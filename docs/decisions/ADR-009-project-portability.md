# ADR-009: Portable project state without operational history replay

**Status:** Accepted  
**Date:** 2026-08-21  
**Deciders:** FORGE maintainers

## Context

Users need to onboard repositories that already exist and move useful FORGE
project state between installations. Database backup and PITR protect a whole
installation, but they are not a safe selective interchange format. Replaying
execution, event or audit rows into another installation would also manufacture
operational history that did not occur there.

## Decision

Define the checksummed `forge-project` format version 1. It carries one project,
active agent assignments, tasks, memories with provenance, and decisions with
stable-key references. Embeddings, executions, context packages, events and
audit rows are explicitly omitted.

Import runs in one PostgreSQL transaction and supports:

- `create`: create a new target, with safe replay of the same bundle;
- `merge`: add missing compatible records without overwriting existing state.

Stable-key collisions with incompatible data fail the complete transaction.
Every successful non-replayed import creates a local event and audit record.

Repository onboarding is a separate, conservative adapter. It accepts bounded
root documentation, common manifests and documentation folders, rejects source
trees and likely secret paths, then records each accepted file as a
provenance-bound project memory. It never modifies the selected repository.

## Consequences

- Projects can be moved without granting filesystem or database backup access.
- Imported operational history remains truthful: the destination records the
  import, but does not pretend source executions occurred locally.
- Embeddings are regenerated by the destination worker for its active profile.
- The format is selective portability, not a substitute for authenticated
  logical recovery or PITR.
- Future format changes require a new format version and explicit parser.
